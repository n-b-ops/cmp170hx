# SPEC-02 — Test catalog and procedures

> Status: specification · Sequence: run T0→T9 in order; each test's pass
> criteria are evaluated in [SPEC-03](SPEC-03-ANALYSIS.md) §5.
> Automatable stages are driven by `scripts/gate.py`; manual fallback commands
> are given for every stage.

## 0. Conventions

### 0.0 Phases

The T-stages group into four phases — hold these in mind rather than a
stage-number sequence:

- **Phase A — Stand & identity** (T0.2 manual pre-unlock enumeration, T1
  `unlock` install+cold boot, the automated post-unlock `intake`
  inventory): *is this the card, and did the unlock happen?* Fully
  enforced only at the third step — `intake` dies unless `memory.total`
  sits in an unlocked band (or 30000–34000 MiB = single-rank finding).
- **Phase B — Card acceptance** (`idle`, `mem_pattern`, `mem_retention`,
  `mem_vulkan`, `burn`, `matmul`, `pcie`, `warm_rerun`): the whole hard-fail gate.
  `matmul` is a synthetic-GEMM determinism fingerprint, **not** inference;
  `warm_rerun` is a heat-soak repeat of mem_pattern+burn under retained
  thermal state, **not** another memtest — it is the last step of Phase B,
  not a separate phase.
- **Phase C — Persistence & workload** (`persistence` T9 manual, `inference` T8
  optional): cold-boot reproducibility of the unlock; then, if the Tier-B
  bundle is carried, the real serving recipe.
- **Phase D — Analysis** (`make-report.py` + `compare-fingerprints.py`):
  post-hoc over the evidence bundle; produces REPORT.md +
  fingerprint.json; **never runs the card**. Analysis is a build artifact,
  not a phase that touches hardware.

### 0.2 Non-negotiable safety rules

1. Stop at **80 °C core** or **85 °C memory** — enforced by the gate's
   watchdog, re-checked post-hoc from telemetry.
2. Stop on **any Xid**, GPU disappearance from `lspci`/`nvidia-smi`, or any
   verification mismatch.
3. **The stand host has exactly one GPU: the card under test** (SPEC-01 §2.1).
   `gate.py` refuses to start otherwise (`--query-compute-apps` must be empty
   fleet-wide) — on a shared/mining host, a neighbor's load confounds card vs
   PSU vs riser vs cooling, and the Xid counters can attribute another GPU's
   faults to our card. If the seller can only offer a mixed host, either move
   the card to a sole-GPU machine, or run the stages manually with explicit
   `-i <index>` and bus-id filtering — and say so in the report's Deviations.
   Degraded in-gate alternative: `gate.py --allow-shared-host --gpu N` pins
   workloads to the card under test via `CUDA_VISIBLE_DEVICES`, keeps Xid
   lines bus-filtered, scopes the compute-clean check to our card, and
   records a forced warn — a shared-host run never reads ACCEPT-clean.
   `--allow-no-dmesg` covers rented containers that cannot read the kernel
   ring: Xid counting is disabled and marked `xid_counting=unavailable`
   (warned in the report; residual risk increased).
4. Power cap asserted and **verified live** before every stage (`nvidia-smi
   --query-gpu=power.limit` → 180 W). The cap silently resets to the vBIOS
   default (250 W) on every reboot and module reload [measured, club].
5. Never run a destructive memory test on a GPU holding someone else's
   workload.
6. A GPU that wedges *without* a temperature rise (stuck compute, dead
   driver thread) can hang both the workload `wait()` and the watchdog's
   `nvidia-smi` probes. Probes carry a 5 s timeout, but the workload wait
   has **no kill timer by design** — one that fires during a healthy long
   burn would be worse. **Ctrl+C is the documented escape**: the gate writes
   an aborted run-summary (→ REJECT-INCOMPLETE) and runs the orphan guards
   on the way out.

### 0.3 Evidence bundle

Everything lands in one timestamped directory (created by `gate.py`, manual
runs use the same layout):

```text
evidence/<date>-<card-tag>/
├── REPORT.md                  generated by make-report.py (final verdict)
├── env/                       OS/kernel/driver/unlock/module inventory (T0/T1)
├── telemetry/*.csv            1 Hz telemetry for the whole session (T2+)
├── xid/xid.log                timestamped kernel watcher output
├── receipts/<stage>.json      per-stage machine-readable results (semantic
│                              names: intake, idle, mem_pattern, …; plus
│                              pcie-after.txt for the T6 after-snapshot)
├── logs/<stage>*.log          raw tool output per stage (matmul artifacts
│                              in logs/matmul*/ subdirectories)
└── photos/                    physical inspection photos (T0.1)
```

## T0 — Intake and inventory (`intake`, 15 min)

### T0.1 Physical inspection (card out of rig, power removed)

Photograph and record (verdict input for SPEC-03 §7):

1. Both sides of the board: warping, discoloration, burnt spots, bulging or
   corroded components, missing/loose heatsink screws, reflow/repair marks.
2. **EPS socket** condition: bent/pushed pins, scorching (wrong-cable damage).
3. PCIe edge-finger: scratches, worn contacts (frequent re-seating wear).
4. Heatsink fins: dust packing, bent fins, evidence of liquid exposure.
   Check whether the thermal pad/paste looks factory or re-pasted.
5. Serial sticker / board part number — the best pure-physical SKU
   discriminator [wiki, board-and-variants]: `900-11001-0108-000` = 8 GB SKU,
   `900-11001-0105-000` = 10 GB SKU. GPU part number sticker: `20C2-105-A1`
   vs `2082-105-A1`. (Club fleet board P/N for the 8 GB SKU matches
   `900-11001-0108-000` [measured].) While photographing, note the **HBM
   vendor** if stack marks are visible: Hynix is the variant validated
   serving recipes use; Samsung-memory cards have community reports of
   Xid 79 under sustained inference load [community-reported,
   vendor/cmp-170hx-vllm] — a Samsung card is a warn-level finding that
   raises the weight of T3/T4/T7 (and of the return window), not an
   automatic reject.
6. **Cap-mod detection** [wiki]: hand-soldered 0402 220 nF caps in designator
   range **C1100–C1350** beside the PCIe gold fingers — 24 = x16 width mod,
   12 = x8, 0 = stock x4. A mod is a data point (rework quality!), not a fail.
7. **Strap-resistor tampering** [wiki]: moved/missing 0402 strap pairs at
   **R986–R1005** (top-left). Miners permuted these; one pattern bricked a
   host. Any non-factory strap work = warn.
8. **Depopulated VRM phases are NORMAL** on this board (A100 PCB depopulated;
   ~3 DrMOS+coils per side absent) — do not read as defect or repair [wiki].
9. PCB warp, scorch marks, fresh flux near the PCIe fingers (hot-air rework
   signature); rusted bracket; salt crust in fins; dust packing; exposed
   gold fingers with worn contact bands (heavy re-seating).

Ask (record answers, verify independently): mining hours counter, thermal or
power events, repairs, why selling.

### T0.2 Enumeration on the stand (before unlock, manual)

This stage is **manual and pre-unlock**. `gate.py` cannot run it: the gate
executes *after* T1 (it demands an unlocked geometry as its own first check,
stage `intake`) — do not confuse the two: T0.2 expects the *stock* memory
band below.

```bash
lspci -nn | grep -iE '10de:20b0|10de:20c2|10de:2082'
nvidia-smi --query-gpu=index,name,pci.bus_id,memory.total,power.limit,temperature.gpu,temperature.memory --format=csv
nvidia-smi -q -i 0 | grep -A3 'VBIOS'
nvidia-smi -q -i 0 | grep -A1 'HW Power Brake Slowdown'
sudo dmesg | grep -Ei 'NVRM|AER|PCIe' || true
```

Pass criteria:

- PCI ID is **10de:20c2** (8 GB SKU, 64 GB target) or **10de:2082** (10 GB SKU,
  40 GB target). **10de:20b0 (A100 SXM4/ES) installs but never unlocks — stop,
  clarify with seller.** Cross-check subsystem ID: 10de:1585 = 8 GB SKU,
  10de:1557 = 10 GB SKU [wiki].
- `memory.total` at stock: 7680–8704 MiB (8 GB SKU) or 9728–10752 MiB
  (10 GB SKU) [cmpunlocker verify.sh bands].
- The installed driver must sit on the pinned unlocker whitelist
  (machine source `pins/drivers.json`, canonical list in PINS.md
  "Driver stack"); `setup-container.sh` automates this check on
  rented instances.
- Record VBIOS string. Known mappings [measured/community, club
  CMP170HX-UNDERSTANDING §4]: `92.00.67.00.01` → HBM NDIV 54 (1458 MHz,
  250 W family); `92.00.6D.00.0A` → NDIV 64 (1728 MHz, 300 W family).
  Also record the **default power limit** (250 vs 300 W) — it identifies the
  VBIOS family when the string is unknown.
- **HW Power Brake Slowdown = Not Active.** If Active with no load: the stand
  (workstation board asserting PWRBRK# on the slot) permanently caps the card
  near ~88 W [measured, club LESSONS §f] — fix the stand (different slot/board)
  before any performance verdict; do not score the card.

### T0.3 Stock-window sanity (before unlock, 5 min, OPTIONAL)

OPTIONAL: needs torch - on a bare stand run it only AFTER the kit venv is
built (MANIFEST s5), or skip it; the unlock verification (T1) covers the
same question. A quick stock-window test proves the card works at all
before software work:

```bash
# 16 GiB is NOT available at stock (8/10 GB window) — smoke within stock:
python3 - <<'EOF'
import torch
a = torch.randn(4096, 4096, device='cuda:0', dtype=torch.bfloat16)
b = torch.randn(4096, 4096, device='cuda:0', dtype=torch.bfloat16)
c = a @ b
torch.cuda.synchronize()
print('stock smoke ok', c.float().mean().item())
EOF
```

Note: stock cards are compute-throttled (FP32 FMA measured ~395 GFLOPS vs
~6,285 GFLOPS patched [community, club RESEARCH]) — performance here is only
a smoke signal, never a verdict.

## T1 — Stand bring-up and unlock (`unlock`, manual; SPEC-01 §4, 30–45 min)

Execute SPEC-01 §4.1–§4.4 (driver 610.43.03 open → cmpunlocker → cold boot →
verification gate). T1 is manual and runs before the gate's evidence
directory exists, so the log paths below are the operator's choice —
`logs/T1/…` matches the printed runbook; copy the captures into the
session bundle's `env/` afterwards (the automated layout convention is
`logs/<stage>/` per §0.3). Evidence captured into `env/`:

```bash
modinfo nvidia | grep -E '^(filename|version):'
cat /lib/modules/$(uname -r)/updates/cmpunlocker/{driver_version,card_profile,unlock_geometry,gpu_inventory} 2>/dev/null
sudo dmesg | grep -E 'SEC2_DEBUG|CMP Gen2|CMP BAR1' > logs/T1/dmesg-unlock.log
cd vendor/cmpunlocker && sudo ./verify.sh 2>&1 | tee ../logs/T1/verify-sh.log
```

Pass criteria (all required):

1. `verify.sh` exit 0: memory in unlocked band (8 GB SKU ≥ 60000 MiB, target
   65536; 10 GB SKU 35000–59999, target 40960) **and** PCIe Gen2 active
   (`pcie.link.gen.current,max` = 2,2).
2. dmesg contains the unlock signature set [wiki procedures/verify, exact
   strings]: `SEC2_DEBUG: saved stock signature`, `POST-WRITE …
   CFG1=0x02779000 LMR=0x0000020b (devId=0x20c2)` (8 GB) / `CFG1=0x02669000
   LMR=0x0000028a` (10 GB), `SEC2_DEBUG: normal BooterLoad status=0x0` — the
   one status that must be zero — `POST-BooterLoad verify`, `WPR meta updated`,
   `late PMA extension status=0x0`, `CMP Gen2: PCIe link trained to Gen2`.
   No `FAILED to open`, no `rebuild stock signature failed`. Line COUNT is not
   a pass/fail signal (healthy captures range 29–152 lines [wiki]).
3. `nvidia-smi` name string: the patched module renames the GPU (name-string
   patch) — record it; deviations flag a different patch set.
4. **Single-rank trap check:** a single-rank 8 GB card caps at 32 GB and the
   unlocker logs a detection line in dmesg [community, club RESEARCH §2a].
   `memory.total` ≈ 32768 MiB → the card is single-rank: **fail/renegotiate**
   (usable capacity half of advertised; T3a will additionally catch fake-64GB
   behavior that Vulkan tests miss).

Fail → diagnosis per SPEC-01 §4.4 (Secure Boot, module shadowing/depmod
ambiguity, cold-boot re-run) — SPEC-03 §3 covers Xid interpretation, not
install failures.

## T2 — Idle baseline (`idle`, 10 min)

With cooling running, cap asserted (180 W), zero load:

```bash
scripts/telemetry.py --duration 600 --out telemetry/idle.csv &   # or gate.py does it
```

Record: mean/max core temp, memory temp, power draw. Reference band for a
healthy card in a cooled stand [measured, club fleet, 180 W cap]:
core 37–38 °C, memory 41–51 °C, 33–41 W. A card far outside this band at idle
(rising idle temp, >55 °C memory) is a warning flag (SPEC-03 §3.2) — passive
cards retain heat, but a hot idle with real airflow also tracks with
leakage-degraded silicon [inferred].

## T3 — HBM2e memory integrity (`mem_pattern` / `mem_retention` / `mem_vulkan`, the decisive test)

> Why this dominates: the unlock exposes fused-off HBM. Field reports put
> used-card failure rates around **~50% in one buyer group**, with faults
> appearing **only above the 8 GiB mining window** [community-reported, club
> LESSONS §h]. A card can mine flawlessly for years and still fail here.

### T3a — CUDA near-full-VRAM pattern test (20–30 min, mandatory)

Vulkan memtest alone is **not sufficient**: single-rank "fake 64 GB" cards
pass memtest_vulkan and fail CUDA tests [community, club RESEARCH §2a].

```bash
nvcc -O3 -arch=sm_80 vendor/club-170hx/scripts/qc/compare_vram.cu -o bin/compare-vram   # once, at T0
bin/compare-vram --device 0 --gib 62        # 8 GB SKU → 64 GB geometry
bin/compare-vram --device 0 --gib 38        # 10 GB SKU → 40 GB geometry
```

Fills and verifies every 64-bit word with an index-derived pattern; exit 0 =
PASS. Any mismatch = **hard fail** — reject regardless of seller explanation
[club LESSONS §h discipline].

### T3b — Retention re-verify (10 min)

After T3a, let the card idle 60 s, then re-run T3a. Catches cells that hold on
first write but decay (marginal refresh/timing) [inferred from the club
vram-gate pattern: write → idle → re-verify].

### T3c — memtest_vulkan full-VRAM pass (duration per profile)

```bash
# via the PTY wrapper (the binary has NO CLI device flag; piped stdin
# silently tests the FIRST-listed device — the classic wrong-card false pass):
python3 vendor/club-170hx/scripts/qc/memtest-select.py 0000:01:00.0 $((3600*PROFILE_H)) logs/T3/memtest.log
```

(`0000:01:00.0` = the card's bus id from T0.2.) The wrapper exits 0 only on
"no any errors … PASSed" **with the correct device confirmed**.

- Exit 64 from memtest_vulkan = **setup error**. `gate.py` retries once
  automatically after clearing orphaned processes; a persistent 64 is recorded
  as **INCOMPLETE** (CONTRACT.md): the memory test never ran, so the verdict is
  CONDITIONAL and cannot be lifted by `--accept-warnings`. **Exception**: if
  the watchdog fired during mem_vulkan (`thermal_stop=1` or `gpu_gone=1`), the stage
  is **FAIL** regardless of the rc=64 setup error — a stop event supersedes
  the setup-error class.
- Orphaned processes pin VRAM after kills (the binary re-execs into a
  detached grandchild) — the wrapper handles process-group kill; for manual
  runs always `pkill -f memtest_vulkan` between attempts.
- Bandwidth line in the summary: record it (informational; community band
  ~1,200–1,600 GB/s depending on source — REFERENCE-NUMBERS §B. Not a gate.)

### T3d — Optional localization on failure (records a receipt)

If T3a/T3c fail: re-run T3a at descending footprints to find the failing
region — 56 GiB, then 32 GiB, then 16 GiB:

```bash
for GIB in 56 32 16; do
  bin/compare-vram --device 0 --gib $GIB 2>&1 | tee logs/T3d-${GIB}gib.log; echo "rc=$?" >> logs/T3d-${GIB}gib.log
done
```

Write `receipts/mem_localize.json` (manual — the run is already a REJECT, this
only feeds the negotiation record):

```json
{ "pass_gib": 32, "fail_gib": 56,
  "interpretation": "errors confined to >32 GiB: upper-stack degradation",
  "logs": ["logs/T3d-56gib.log", "logs/T3d-32gib.log", "logs/T3d-16gib.log"] }
```

Errors confined to the top region = degradation of the last stacks; errors at
small footprints = broader damage. Either way any error in the unlocked window
is a hard fail (SPEC-03 §5) — localization never rescues a card, it only
sharpens the conversation with the seller.

## T4 — Compute burn and thermal validation (`burn`, per profile duration)

```bash
sudo nvidia-smi -i 0 -pl 180 && nvidia-smi -i 0 --query-gpu=power.limit --format=csv,noheader   # assert
bin/gpu-burn/gpu-burn -tc -c bin/gpu-burn/compare.fatbin $((60*BURN_MIN)) 2>&1 | tee logs/T4/gpu-burn-tc.log
```

- `-tc` = tensor-core burn (the club's measured mode). Expected result:
  **0 errors**, sustained **74.6–78.5 TFLOP/s** at 180 W on a 70-SM unlock
  [measured, club health gate]; the pinned unlocker enables 74 SMs (+4) —
  expect equal or slightly higher; **< 70 TFLOP/s sustained is a warning,
  < 60 is a fail** (SPEC-03 §5).
- Temperatures from telemetry: peak core/mem compared against SPEC-03 §3.1
  bands; with proper airflow expect ≤ 71 °C mem at 180 W [measured, club].
- **FP32 mode is not a cooling validation** — plain FP32 draws ~60 W on this
  card [community]; tensor burn is the load that reaches the cap.
- At a reduced cap (SPEC-01 §2.2 degraded stand, < 150 W) the TFLOPS floors
  do not apply: `gate.py --power-w 125` records `tflops_gate=informational`
  and a WARN-class verdict (floors are 180 W-calibrated); thermal and error
  channels still gate, and the cap-independent dead-card floor (< 20
  TFLOP/s = failed compute unlock, REFERENCE-NUMBERS §C) still FAILs. The
  run is recorded as stand-limited.
- Optional (Standard/Extended, if stand cooling is proven): short FP64 stage
  `gpu-burn -d 600` — the classic full-power envelope test from the original
  roadmap; frame results as stand-conditioned. Expected: **6.2–6.31 TFLOPS**
  non-tensor FP64 (exactly ½ of the 12.2–12.8 TFLOPS FP32, both fully
  restored post-unlock [wiki, multiple testers]); `gpu_burn -m 63500 -d 30`
  (0 memory errors) is the wiki's memory-stressed FP64 recipe.
- Optional 250 W stage (manual - not in the gate stage list; 10 min,
  Extended only, requires proven airflow):
  informational — validates the stock envelope but thermals say as much about
  the stand as the card.

## T5 — Tensor-core correctness fingerprint (`matmul`, 15 min)

Single-card adaptation of the club's cross-card identity gate [club QC §3b]:

```bash
python3 scripts/matmul_check.py 0 170170 logs/T5/   # gate.py ships this (club matmul_check.py adapted)
# The interpreter MUST have torch+CUDA (kit venv; set TG_MATMUL_PYTHON) -
# plain python3 on a fresh stand has no torch and T5 will be SKIPPED.
# The script also gates BF16 throughput (>=100 TFLOPS pass, 80-100 warn,
# <80 fail - inferred single-op thresholds, CONTRACT.md matmul).
```

1. Same-seed (170170) BF16/FP16/TF32/INT8 4096×4096 matmuls vs CPU float64
   reference; record max-abs-err per dtype.
   Reference values (torch 2.13.0+cu130, 4 cards, 70-SM stack) [measured]:
   BF16 1.348 / FP16 0.166 / TF32 0.098 / INT8 0. The +4-SM stack may shift
   values slightly (different cuBLAS tiling) — the **fingerprint** is:
   no NaN/Inf, each dtype within ~2× of the reference value, INT8 exactly 0.
2. **Determinism**: repeat 3×; results must be **bit-identical** across
   repeats (this replaces the club's cross-card identity signal — a real
   tensor-core fault shows up as non-deterministic or wildly-off results).

## T6 — PCIe and AER deltas (`pcie`, 5 min, automated around T3/T4)

```bash
vendor/club-170hx/scripts/qc/pcie-check.sh > receipts/T6-pcie-after.txt
lspci -vv -s <bus> | grep -E 'DevSta|UESta|CESta' > receipts/T6-aer-after.txt
sudo nvidia-smi -q -i 0 | grep -A1 Replay >> receipts/T6-pcie-after.txt
```

Compare before/after (the gate snapshots at the intake and pcie stages): **zero** uncorrectable AER,
**zero climbing** correctable counters, zero replay delta, link still Gen2 x16
(or the stand's trained width — record it; x8 on lane-sharing boards is
topology, not fault [measured, club]).

## T7 — Warm rerun (`warm_rerun`, 30 min)

Without reboot, re-run: T3a (compare_vram 62 GiB) + T4 short burn (10 min).
Pass = identical criteria. A card that passes cold but fails warm has a
heat-soak-dependent defect — reject [club QC stage-4 discipline].

## T8 — Tier B: real-workload gate (`inference`, optional, 60–90 min)

Only if the Standard/Extended window allows and the kit's model bundle is
carried. Full pins in club `recipes/qwen3.8-27b-dflash2` (recipe.json):
vLLM 0.27.1 + patch set, model `dbirks/Qwen3.8-27B-W4A16-AutoRound` @
`1f05c441` + DFlash2 overlay `124c14e7` + draft `4d30ec73`, 180 W cap.

**Kit path**: the fetch -> install -> smoke sequence, sizes, and per-step
details live in one place — [kit/inference/README.md](../kit/inference/README.md)
(the acceptance recipe and the informational recipes). Verdict semantics
here: rc=1 below 0.9× a floor — the report forces CONDITIONAL (CONTRACT
T8 row); 0.9×–floor records rc=0 plus a `warn` field, which machine-reads
WARN-INFERENCE (never a clean PASS).

**Informational companions** (`kit/inference/recipes/`): non-acceptance
serving recipes (Qwen3.6-35B-A3B-FP8, Nemotron-3.5-Lightning-30B-A3B)
provisioned by `fetch-model.sh`/`install-model.sh` and run by
`smoke-model.py` — same usage-counted protocol, receipts named
`inference-<key>.json` with rc=0 on protocol completion. Their anchors
are community/lab-reported (REFERENCE-NUMBERS §E) and are NEVER CONTRACT
floors; the test suite enforces that classification.

**sm80 DFlash2 driver rule**: prefer 610.43.03 (the club-validated
pin) or 610.57.04 for T8 — the community fault reports (both closed)
were on 610.43.02, and a third box on 610.57.04 could not reproduce
either fault; the smoke guard stops on any Xid and the gate scores
Xid 31 as a hard fail [measured class, CONTRACT]. Reproduction links
and full evidence: REFERENCE-NUMBERS §0, `kit/inference/recipe.json`
cautions, and kit/inference/README "Safety and cautions".

Run the recipe's benchmark ladder (decode256 ×3, decode900 ×3, prefill@6.6k,
warm). Serve with `--gpu-memory-utilization` **≤ 0.90** — 0.95 crashed a card
on the unlocked geometry (65052 MB exposed, 64733 MB usable) [wiki]. Acceptance
band @180 W, 64k ctx [measured, club, 3 cards]:

| Metric                          | Band                | Floor (fail below) |
| ------------------------------- | ------------------- | ------------------ |
| decode256 tok/s (median of 3)   | 133.6–140.3         | 130                |
| decode900 tok/s                 | 118–125             | 112                |
| prefill @ ~6.6k in, tok/s       | 1,930–1,960         | 1,750              |
| TTFT warm (256-token gen)       | ~190 ms             | 250 ms             |

Methodology traps that produce false fails [club, measured]: discard the
first request after server start (JIT warmup); tokens from the final usage
object, never SSE event counts; 3+ repetitions; no other load on the host.

Context numbers (different stacks — **not** comparable, do not gate on them):
Qwen3.8-27B GGUF megakernel ~51–94 tok/s; llama.cpp Qwen3.8-Flash-Next
53.4 tok/s; Ninfer 38 tok/s [all measured, club, different recipes]; the
300 W VBIOS bench dataset's Qwen3.6-27B W4A16 ~130–140 tg (MTP k=3) and
35B-A3B MoE ~205 tg [community-reported, different model generation —
REFERENCE-NUMBERS §E].

### T8b — Concurrency smoke (optional, Extended; informational, not a gate)

The original motivation for this card includes serving several sessions; a
cheap sanity check that concurrency doesn't wedge the stack (historically:
`shm_broadcast` engine deaths at c=4–8 with no Xid [club]):

